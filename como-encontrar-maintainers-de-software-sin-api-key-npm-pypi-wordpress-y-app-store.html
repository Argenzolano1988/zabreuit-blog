Cómo encontrar maintainers de software sin API key (npm, PyPI, WordPress y App Store)

Los maintainers de paquetes y extensiones son una lista de contactos B2B que nadie compra: son públicos, están segmentados por tecnología y se actualizan solos. El problema no es el acceso, es que cada registro tiene forma distinta y la mitad de los campos de contacto vienen vacíos.

Si vendés infraestructura, herramientas de desarrollo, auditorías o servicios de scraping, apuntar a quien mantiene un paquete con 50.000 descargas mensuales es mejor que comprar 10.000 emails genéricos. Esta guía cubre las cuatro fuentes que devuelven datos de contacto por HTTP simple, sin credenciales: el registry de npm, la API JSON de PyPI, el directorio de plugins de WordPress.org y la API de búsqueda de la App Store.

Qué se consigue y qué no

Sin credenciales, de forma estable:

  • npm: nombre del paquete, versión, repositorio, fecha del último release y la lista de maintainers con email cuando el proyecto lo declaró.
  • PyPI: autor, email de autor, URLs del proyecto y todas las versiones publicadas.
  • WordPress.org: autor del plugin, perfil público, instalaciones activas y valoraciones.
  • App Store: nombre del vendedor, su web y el identificador de artista de Apple.

Lo que no se consigue: emails personales que el autor no publicó, teléfonos, datos de facturación, ni nada detrás de un login. Tampoco hay endpoint de "lista de todos los maintainers de un ecosistema": hay que barrer por búsqueda, y cada ecosistema limita cuánto te deja barrer por minuto.

Paso 1 — npm: del paquete al maintainer

El registry devuelve el packumento completo del paquete en registry.npmjs.org/<nombre>. Ahí está maintainers, que es un array de {name, email}. Lo importante: name y username son campos distintos según la antigüedad del paquete, y el email puede no estar.


// npm-maintainers.mjs — uso: node npm-maintainers.mjs cheerio react
const pkgs = process.argv.slice(2);

async function packument(name) {
  const res = await fetch('https://registry.npmjs.org/' + encodeURIComponent(name).replace('%40', '@'), {
    headers: { Accept: 'application/vnd.npm.install-v1+json, application/json' },
  });
  if (res.status === 404) return null; // paquete inexistente o unpublished
  if (!res.ok) throw new Error('HTTP ' + res.status + ' en ' + name);
  return res.json();
}

for (const name of pkgs) {
  const doc = await packument(name);
  if (!doc) { console.log(name, 'no existe'); continue; }
  const latest = doc['dist-tags']?.latest;
  const maintainers = (doc.maintainers || []).map((m) => ({
    handle: m.name || m.username,
    email: m.email || null,
  }));
  console.log(name, latest, JSON.stringify(maintainers));
}

Dos trampas que cuestan un falso positivo cada cien leads:

  • Accept: application/vnd.npm.install-v1+json devuelve el documento abreviado, que no incluye maintainers. Si pedís esa variante, maintainers viene vacío y parece que el paquete no tiene dueño.
  • El usuario que publica el último release (_npmUser) no es necesariamente el maintainer. Un bot puede haberlo publicado: en un barrido real aparecen publishers llamados GitHub Actions. Filtrá handles de bots antes de escribirles.

Para descubrir paquetes en lugar de partir de una lista conocida, está la búsqueda: https://registry.npmjs.org/-/v1/search?text=keywords:scraper&size=250. Devuelve objects[].package con name, publisher.username, date y links. El filtro text=keywords:... es el que sirve: buscar por texto libre trae paquetes abandonados con el término en el README.

Paso 2 — PyPI: el email viene dentro del string

PyPI expone https://pypi.org/pypi/<proyecto>/json. El campo info.author suele venir en null y el contacto real está en info.author_email, con formato Nombre <email>. Hay que parsearlo, no concatenarlo.


// pypi-owner.mjs — uso: node pypi-owner.mjs requests django
async function pypi(project) {
  const res = await fetch('https://pypi.org/pypi/' + project + '/json');
  if (res.status === 404) return null;
  if (!res.ok) throw new Error('HTTP ' + res.status + ' en ' + project);
  return res.json();
}

const parseEmail = (s) => s?.match(/<([^>]+)>/)?.[1] ?? (s?.includes('@') ? s.trim() : null);

for (const project of process.argv.slice(2)) {
  const doc = await pypi(project);
  if (!doc) { console.log(project, 'no existe'); continue; }
  const { info, releases } = doc;
  const versions = Object.keys(releases || {});
  console.log({
    project,
    version: info.version,
    author: info.author || info.maintainer || null,
    email: parseEmail(info.author_email || info.maintainer_email),
    homepage: info.project_urls?.Homepage || info.home_page || null,
    versions: versions.length,
  });
}

Advertencia de calidad de datos: en proyectos grandes author suele ser null y author_email trae una dirección institucional (Django Software Foundation <foundation@djangoproject.com>), no la de una persona. Eso no es basura: para vender soporte o auditoría, una casilla institucional convierte mejor que la personal. Lo que no sirve es asumir que el campo author tiene algo — en tres de cada cuatro proyectos del top 100 está vacío.

releases te da la señal de actividad sin descargar nada: si la última versión tiene más de un año y el proyecto tiene 90 versiones, el maintainer está inactivo y no es un lead de compra, es un lead de fork.

Paso 3 — WordPress.org: el autor viene en HTML

El directorio de WordPress no tiene API REST, pero sí una API de lectura con parámetros estilo PHP: https://api.wordpress.org/plugins/info/1.2/?action=query_plugins&request[search]=seo&request[per_page]=100.


// wp-authors.mjs — uso: node wp-authors.mjs seo backup
const q = new URLSearchParams({ action: 'query_plugins' });
q.set('request[search]', process.argv[2] || 'seo');
q.set('request[per_page]', '100');

const res = await fetch('https://api.wordpress.org/plugins/info/1.2/?' + q);
if (!res.ok) throw new Error('HTTP ' + res.status);
const { plugins = [], info = {} } = await res.json();

const strip = (html) => String(html || '').replace(/<[^>]*>/g, '').trim();

console.log('resultados:', info.results, 'de', info.pages, 'páginas');
for (const p of plugins) {
  console.log({
    slug: p.slug,
    active_installs: p.active_installs,
    author: strip(p.author).split(/[,&]/)[0].trim(), // "Rank Math SEO" en vez del <a href>
    profile: p.author_profile,                        // /plugins/author/<usuario>/
  });
}

Los corchetes de request[...] tienen que ir codificados: si los mandás crudos, algunos clientes los normalizan y la API responde como si no hubieras filtrado nada. Y author trae un enlace HTML completo — sin strip, ese campo te ensucia toda la lista con markup y el deduplicado por nombre falla.

active_installs es el mejor filtro de priorización del directorio: es un entero redondeado (1000, 10000, 4000000), así que cortá en 10000 o más si querés leads con presupuesto. Para un plugin puntual, action=plugin_information&request[slug]=<slug> devuelve además author_profile, que es el usuario de WordPress.org con el que se puede enriquecer después.

Paso 4 — App Store: vendedor y web, no email

La API de búsqueda de Apple devuelve JSON sin credenciales: https://itunes.apple.com/search?term=<término>&entity=software&limit=200. El máximo por consulta es 200 y no hay paginación real: para más, hay que segmentar por término y por país (country=).


// appstore-vendors.mjs — uso: node appstore-vendors.mjs factura
const term = process.argv[2] || 'invoice';
const url = 'https://itunes.apple.com/search?' + new URLSearchParams({
  term,
  entity: 'software',
  country: 'es',
  limit: '200',
});

const res = await fetch(url);
if (!res.ok) throw new Error('HTTP ' + res.status);
const { resultCount, results = [] } = await res.json();

const seen = new Map();
for (const app of results) {
  if (!seen.has(app.sellerName)) {
    seen.set(app.sellerName, {
      seller: app.sellerName,
      web: app.sellerUrl || null,
      artistId: app.artistId,
      apps: 0,
    });
  }
  seen.get(app.sellerName).apps++;
}

console.log(resultCount, 'apps de', seen.size, 'vendedores');
console.log([...seen.values()].sort((a, b) => b.apps - a.apps).slice(0, 10));

La API no da email ni nombre de contacto: da sellerName, sellerUrl y artistId. Se usa como semilla: la web del vendedor se scrappea con las mismas herramientas que cualquier otro sitio, y artistId agrupa todas las apps del mismo desarrollador, que es la señal de que hay una empresa detrás y no un proyecto de fin de semana.

Un detalle que rompe la deduplicación: el mismo desarrollador publica con nombres distintos por país. Si consultás varios country=, agrupá por artistId, no por sellerName.

Cerrar el pipeline: normalizar antes de escribir

Las cuatro fuentes devuelven la misma entidad con cuatro formas. Antes de guardar, una sola clave:


// normalize.mjs
const domainOf = (u) => {
  try { return new URL(u).hostname.replace(/^www\./, '').toLowerCase(); } catch { return null; }
};

export function lead(source, { email, name, url, handle }) {
  return {
    source,                                  // npm | pypi | wordpress | appstore
    email: email ? email.trim().toLowerCase() : null,
    domain: domainOf(url),
    handle: handle || null,
    // Clave de dedupe: el email manda; si no hay, dominio; si no, plataforma+handle.
    key: email
      ? 'e:' + email.trim().toLowerCase()
      : domainOf(url)
        ? 'd:' + domainOf(url)
        : handle
          ? 'p:' + source + ':' + handle
          : null,
  };
}

Tres reglas que evitan trabajo inútil:

  • Descartá leads con key === null. Sin email, dominio ni handle no hay a quién escribir.
  • Un mismo dominio puede aparecer como maintainer de npm y como autor de un plugin de WordPress. Eso no es ruido: es la señal más fuerte de que hay una empresa con varios productos.
  • No mandes nada el mismo día que barrés. Un email a maintainers[0].email de un paquete sin actividad en 18 meses es una queja de spam esperando a pasar.

Costo y límites reales

Ninguna de las cuatro fuentes tiene cuota comercial ni pide token. Todas aplican cortesía: una petición por recurso, sin bucles por segundo, y un User-Agent que identifique la aplicación con un contacto. El registry de npm y PyPI devuelven 429 si abusás; WordPress.org responde lento con per_page alto, así que conviene 100 y no 250.

El costo verdadero no es el acceso: es el mantenimiento. Los endpoints cambian de forma (PyPI ya mudó de home_page a project_urls), los campos de contacto se vacían y los paquetes se transfieren de dueño. Un barrido que corre una vez y se guarda en un CSV queda obsoleto en un mes.
