Cómo leer precios y stock de una tienda WooCommerce sin API key

La Store API pública de WooCommerce devuelve catálogo, precio y stock en JSON sin credenciales. Ruta, unidades de precio y trampas medidas.

Hoy, 18 de noviembre de 2026, la GoPro Mission 1 Pro Grip Edition figura en gopro.com.ar a ARS 2.049.999, rebajada desde 2.099.999. El mismo catálogo público muestra 24 productos en oferta sobre 85 visibles. Todo eso salió de una URL que no pide token, cookie ni usuario: la Store API que WooCommerce usa para pintar su propio carrito.

WooCommerce corre sobre WordPress y expone dos APIs distintas. La REST API clásica (wc/v3) exige consumer key y secret: sirve para crear pedidos, leer clientes y escribir stock. La Store API (wc/store/v1) es la que alimenta el storefront, así que es pública por diseño: catálogo, variantes, precios, disponibilidad y reseñas. Para monitorear precios alcanza con la segunda.

La ruta y cómo saber si está abierta

La ruta base es /wp-json/wc/store/v1/products. En gopro.com.ar responde así:


curl -s "https://gopro.com.ar/wp-json/wc/store/v1/products?per_page=2" | head -c 400

Si el sitio no usa enlaces permanentes bonitos, la misma ruta existe como parámetro:


curl -s "https://gopro.com.ar/?rest_route=/wc/store/v1/products&per_page=1"

Comprobé las dos en la misma tienda y devuelven el mismo JSON. Antes de escribir el parser conviene descartar tres casos:

  • No es WordPress. La ruta devuelve 404 o el HTML de la home.
  • Es WordPress sin WooCommerce. El JSON trae {"code":"rest_no_route"}. El sitio responde, pero no hay catálogo.
  • WooCommerce con REST cerrado. Algún plugin de seguridad cierra /wp-json/ a los no logueados. En porta.com.ar, que sí es WordPress, /wp-json/ devuelve directamente HTML. No hay forma de leer el catálogo sin credenciales y ahí conviene parsear la ficha.

Un detalle que ahorra tiempo: GET /wp-json/ lista los namespaces activos. Si aparece wc/store/v1, la tienda tiene la API abierta.

El precio no viene en pesos: viene en unidades mínimas

Este es el error que rompe todos los monitores nuevos. El campo prices.price es un string entero en la unidad mínima de la moneda, y prices.currency_minor_unit dice cuántos decimales mover.

En gopro.com.ar, un producto de ARS 44.999 se ve así:


"prices": {
  "price": "44999",
  "regular_price": "44999",
  "sale_price": "44999",
  "currency_code": "ARS",
  "currency_minor_unit": 0
}

En woocommerce.com, que vende en dólares, el mismo campo trae "price": "19900" con currency_minor_unit: 2. Son USD 199,00, no 19.900. El peso argentino y el chileno usan cero decimales; el dólar y el euro, dos. Si dividís siempre por 100, en Argentina te quedan precios 100 veces más chicos y el monitor avisa cualquier cosa.

La fórmula que usé en el script es una sola:


const valor = Number(p.prices.price) / 10 ** Number(p.prices.currency_minor_unit);

on_sale y regular_price permiten calcular el descuento sin adivinar: si on_sale es true, price ya viene rebajado y regular_price es el precio de lista.

Las variantes no traen su precio

El producto padre de tipo variable devuelve un array variations[] con id y attributes, nada más. El precio y el stock de cada talle o color están en su propio endpoint:


curl -s "https://gopro.com.ar/wp-json/wc/store/v1/products/68907"

Esa respuesta tiene type: "variation", parent: 55852 y su bloque prices completo. En la máscara de snorkel que medí, las cuatro variantes (azul y verde, en dos talles) salían ARS 44.999 cada una y el padre mostraba el mismo número, con price_range en null. En zulki.com.ar el mismo campo sí viene completo: el Bloque de Hielo tiene precio padre 28.500 y price_range de 28.500 a 38.000, porque la variante grande sale 38.000 y la mediana 28.500. O sea: price_range sirve cuando está, pero no se puede asumir que esté.

El stock también es por variante. La Botella Térmica 0.530 de esa tienda trae is_in_stock: false en el padre y en las cinco variantes, con stock_availability.text en "Agotado". Si el script solo mira el padre, acierta; cuando el padre está en stock y una variante no, no.

Consecuencia práctica: si el precio cambia por variante, el script necesita una request extra por variante. En un catálogo de 500 productos variables eso son cientos de llamadas, y ahí el per_page=100 deja de ser el número que importa.

El sku del padre puede venir vacío y el de la variante no: en gopro.com.ar el producto padre tenía sku: "" y la variación OUT515L/XLB. Para cruzar con un ERP, el SKU de la variante es el identificador útil.

Paginación: 100 por página y dos headers

El máximo es 100. Pedir per_page=101 devuelve 400 con el mensaje exacto: per_page debe estar entre 1 (incluido) y 100 (incluido). No hay que adivinarlo ni reintentar.

El total está en los headers de la respuesta:


curl -sI "https://woocommerce.com/wp-json/wc/store/v1/products?per_page=100" | grep -i x-wp-total
# x-wp-total: 1807
# x-wp-totalpages: 19

Ese es el catálogo real de woocommerce.com: 1.807 productos en 19 páginas. gopro.com.ar tiene 85 y zulki.com.ar 31, así que entran en una sola llamada. Para recorrer todo:


let page = 1, totalPages = 1;
do {
  const res = await fetch(`${base}/wp-json/wc/store/v1/products?per_page=100&page=${page}`);
  totalPages = Number(res.headers.get("x-wp-totalpages") || 1);
  const productos = await res.json();
  // procesar productos
  page++;
} while (page <= totalPages);

Los filtros que funcionan sin credenciales y que probé: search=, category=<id>, orderby=price&order=asc y page=. El orden por precio sirve para vigilar el extremo barato del catálogo sin bajar los 1.800 productos enteros.

El script completo

Node 18 o superior, sin dependencias. Guarda CSV por stdout y deja el progreso por stderr:


// woo-precios.mjs — node woo-precios.mjs https://tienda.com > catalogo.csv
const base = (process.argv[2] || "").replace(/\/$/, "");
if (!base) throw new Error("uso: node woo-precios.mjs https://tienda.com");

async function get(url, intentos = 3) {
  for (let i = 1; i <= intentos; i++) {
    const res = await fetch(url, { headers: { accept: "application/json" } });
    if (res.ok) return res;
    if (res.status === 429 || res.status >= 500) {
      await new Promise((r) => setTimeout(r, 1000 * i));
      continue;
    }
    throw new Error(`${res.status} ${url}`);
  }
  throw new Error(`sin respuesta tras ${intentos} intentos: ${url}`);
}

const filas = [];
let page = 1, totalPages = 1;
do {
  const res = await get(`${base}/wp-json/wc/store/v1/products?per_page=100&page=${page}`);
  totalPages = Number(res.headers.get("x-wp-totalpages") || 1);
  const productos = await res.json();

  for (const p of productos) {
    const { price, regular_price, currency_code, currency_minor_unit } = p.prices;
    const unidad = 10 ** Number(currency_minor_unit);
    filas.push({
      sku: p.sku || "",
      nombre: p.name,
      tipo: p.type,
      precio: Number(price) / unidad,
      lista: Number(regular_price) / unidad,
      moneda: currency_code,
      en_stock: p.is_in_stock ? "si" : "no",
      variantes: p.variations?.length || 0,
      url: p.permalink,
    });
  }
  console.error(`página ${page}/${totalPages}: ${productos.length} productos`);
  page++;
  await new Promise((r) => setTimeout(r, 300));
} while (page <= totalPages);

const cols = Object.keys(filas[0]);
const csv = [cols.join(","), ...filas.map((f) => cols.map((c) => JSON.stringify(String(f[c]))).join(","))].join("\n");
console.log(csv);

El sleep de 300 ms no es decorativo. Después de tres o cuatro consultas seguidas en un par de minutos, zulki.com.ar me devolvió 403; el mismo endpoint había contestado 200 antes. No sé si fue el WAF del hosting o un plugin de seguridad, pero el patrón se repite en tiendas chicas con hosting compartido: ráfaga corta, bloqueo, y hay que esperar.

Qué no vas a encontrar ahí

  • Productos ocultos del catálogo. La API devuelve lo que el storefront muestra. Si la tienda oculta un ítem o lo marca como privado, no aparece.
  • Precios por cliente. Las listas mayoristas o los descuentos por rol viven en la REST API autenticada. La Store API siempre devuelve el precio público.
  • Costo y margen. No están en ningún endpoint público, por diseño.
  • Historial. Cada llamada es una foto. Para ver evolución hay que guardar las corridas y comparar; la API no recuerda nada.

Con eso ya se puede montar un monitor semanal de 100 tiendas: 100 requests de catálogo, un archivo por fecha y un diff contra la semana anterior. Lo que no se puede improvisar es la parte aburrida: reintentos, rotación de proxies cuando el hosting bloquea, y normalizar el mismo producto entre tiendas distintas, que suele resolverse por EAN y no por SKU.
