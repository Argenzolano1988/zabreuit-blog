Cómo leer precios y stock de una tienda VTEX sin API key ni browser

Las tiendas VTEX publican catálogo y precios en JSON sin autenticación. Endpoint, paginación de 50, canal de venta y las trampas medidas en tiendas reales.

La misma oblea cuesta distinto según el banner. Hoy, 11 de noviembre de 2026, consulté el catálogo público de Jumbo, Disco y Vea buscando el mismo EAN —7891000248799, Oblea KitKat 4 Fingers— y salieron tres precios: 3.000, 3.050 y 2.890 pesos. Mismo producto, mismo grupo empresario, 5,5% de diferencia entre el más caro y el más barato, y ninguna de las tres páginas lo muestra.

Ese es el trabajo real de un monitor de precios en LatAm: no leer un precio, sino sostener la lectura de cientos de SKUs repartidos en varias tiendas y canales, con el mismo identificador y en el mismo momento. Para VTEX no hace falta ni API key ni browser.

Por qué el JSON está a la vista

VTEX es la plataforma de e-commerce enterprise más extendida de la región: farmacias, supermercados, retail de electrónica, marketplaces. El storefront de VTEX IO se renderiza en el cliente, así que el HTML que devuelve el servidor trae el precio de la primera pintura: una página, un canal de venta, sin el total de resultados y sin los otros vendedores del mismo ítem.

El catálogo, en cambio, está publicado como JSON en una ruta fija, sin autenticación, sin cookie y sin token:


curl "https://www.jumbo.com.ar/api/catalog_system/pub/products/search/?ft=kitkat&_from=0&_to=9"

Eso devuelve un array de productos con precio, stock, EAN y vendedor. La ruta se repite en los dominios VTEX que probé: jumbo.com.ar, disco.com.ar, vea.com.ar, fravega.com, cetrogar.com.ar y farmacity.com.

La estructura que importa

Cada producto del array trae un objeto items[] (variantes) y cada ítem trae sellers[]. El precio no está en el producto: está en la oferta comercial de cada vendedor.


{
  "productId": "241361",
  "productName": "Oblea Leche 4 Fingers 41.5 Grs Kitkat®",
  "linkText": "oblea-leche-4-fingers-41-5-grs-kitkat-2",
  "items": [{
    "ean": "7891000248799",
    "unitMultiplier": 1,
    "sellers": [{
      "sellerName": "Jumbo Argentina IO",
      "commertialOffer": {
        "Price": 3000,
        "PriceWithoutDiscount": 3000,
        "ListPrice": 3000,
        "IsAvailable": true,
        "AvailableQuantity": 99999
      }
    }]
  }]
}

Cuatro cosas de ahí, en orden de importancia:

  • Price viene en unidades de la moneda, no en centavos: 5900 es ARS 5.900. Y viene con decimales reales (6114.05), así que no lo redondees al leer.
  • IsAvailable y AvailableQuantity son del vendedor, no de la tienda. Un ítem puede estar publicado y no tener stock.
  • unitMultiplier cambia la unidad. En "Banana Ecuador X Kg" medí 0.5: el precio es por medio kilo. Si multiplicás por el tamaño del pack sin mirar este campo, el precio unitario sale mal.
  • El productId solo es único dentro de la cuenta. Para cruzar cadenas distintas el identificador es el ean.

Las trampas que aparecen en la primera hora

Todas las siguientes las choqué midiendo, no leyendo documentación.

301 entre dominios. farmacity.com.ar redirige a farmacity.com. Con curl sin -L recibís un 301 con cuerpo vacío y parece que la API no existe. fetch sigue redirecciones por defecto; curl no.

La respuesta es 206, no 200. La cabecera resources confirma el rango servido. Si tu chequeo es status === 200, el script se cae en la primera llamada. Usá res.ok, que cubre 200 y 206.

_to no pasa de 49. Pedir _to=50 devuelve HTTP 400 con el texto exacto "Parameter _to can't be greater than 50." Son 50 productos por request, ni uno más.

_from se corta en 2500. Arriba de eso: "Parameter _from can't be greater than 2500." Una búsqueda con 2.669 resultados —"celular" en Frávega— no se puede recorrer con una sola query. Hay que partir por categoría, marca o rango de precio.

El canal de venta cambia el resultado, y falla en silencio. En Farmacity, ?fq=productId:240916 sin sc devuelve el producto; con sc=1 devuelve [] y HTTP 200. Un array vacío no es un error: es la peor forma de fallar. Si tu monitor usa canales de venta, guardalos en la config y probá cada uno.

Un vendedor sin stock reporta precio 0. En un celular de Frávega aparecieron dos ofertas: MaxiHome a 97.799 con stock 100 y Frávega a 0 con stock 0. Tomar sellers[0] sin filtrar mete un cero en el promedio y te hace concluir que el precio se derrumbó.

ListPrice viene inconsistente. En un ítem de Jumbo medí Price: 999 junto a ListPrice: 90407, un valor que no corresponde a ningún precio de lista plausible. Para comparar sirve Price; para detectar descuento, PriceWithoutDiscount.

Caché de cinco minutos. La respuesta trae x-vtex-apicache-time: 300. Un cron cada 60 segundos golpea la misma copia y no ve nada nuevo.

El WAF no es VTEX. nike.com.ar responde 403 con la página "Just a moment..." de Cloudflare sobre la misma ruta. Es el WAF delante del sitio. Reintentar más fuerte empeora las cosas.

El script

Node 18+, cero dependencias. Itera de a 50, corta en el total que informa la cabecera resources (0-9/112 significa "te di 10 de 112"), descarta vendedores sin stock y emite CSV para abrir en Sheets.


const [, , base, query = "", max = "200"] = process.argv;
const sleep = (ms) => new Promise((r) => setTimeout(r, ms));
const csv = (v) => `"${String(v ?? "").replace(/"/g, '""')}"`;

async function page(from) {
  const url = `${base}/api/catalog_system/pub/products/search/?ft=${encodeURIComponent(query)}&_from=${from}&_to=${from + 49}`;
  for (let attempt = 1; attempt <= 3; attempt++) {
    const res = await fetch(url, { headers: { Accept: "application/json", "User-Agent": "price-check/1.0" } });
    if (res.ok) {
      const total = Number(res.headers.get("resources")?.split("/")[1] ?? 0);
      return { products: await res.json(), total };
    }
    if (res.status === 400) throw new Error(`${res.status}: ${await res.text()}`);
    await sleep(800 * attempt);
  }
  throw new Error(`sin respuesta para _from=${from}`);
}

const rows = [];
let from = 0;
while (from <= 2500 && rows.length < Number(max)) {
  const { products, total } = await page(from);
  for (const p of products) {
    for (const item of p.items ?? []) {
      for (const s of item.sellers ?? []) {
        const offer = s.commertialOffer ?? {};
        if (!offer.IsAvailable || !(offer.Price > 0)) continue;
        rows.push([base.replace(/^https?:\/\//, ""), p.productId, item.ean || "",
          p.productName, s.sellerName, offer.Price, offer.AvailableQuantity,
          `${base}/${p.linkText}/p`]);
      }
    }
  }
  from += 50;
  if (from >= total) break;
  await sleep(300);
}

console.log(["tienda", "productId", "ean", "nombre", "vendedor", "precio", "stock", "url"].join(","));
for (const r of rows) console.log(r.map(csv).join(","));

Correrlo contra las tres cadenas deja los precios uno al lado del otro:


node vtex-prices.mjs https://www.jumbo.com.ar kitkat > jumbo.csv
node vtex-prices.mjs https://www.disco.com.ar kitkat > disco.csv
node vtex-prices.mjs https://www.vea.com.ar  kitkat > vea.csv

Dónde esto no alcanza

  • Tiendas con la ruta desactivada. Algunas cuentas cierran el catálogo público: 403 o 404 en la ruta. Ahí no hay atajo, toca sitemap + JSON-LD o la API oficial con credenciales.
  • Catálogos grandes. El tope de _from en 2500 obliga a segmentar. Un supermercado con 40.000 SKUs son decenas de queries por categoría, no una.
  • Solo catálogo público. No hay checkout, no hay precios con login, no hay listas B2B. Para precios por cliente la ruta es otra y requiere credenciales del retailer.
  • Cortesía mínima. Un request cada 300 ms con tres reintentos y un User-Agent identificable alcanza. Machacar el endpoint es la forma más rápida de que te bloqueen y de romper el sitio para el resto.
  • Reglas de cada sitio. Es data pública de catálogo, pero cada tienda tiene sus términos y su robots.txt. Revisalos antes de programar un cron: en Jumbo, Disco y Vea el bloqueo alcanza a /Busca/, /login y /checkout, no a la ruta de la API. Eso puede cambiar sin aviso.

Si el problema es un SKU o una tienda, el script de arriba sobra. Cuando son ocho plataformas —VTEX, Shopify, WooCommerce, Magento, Tiendanube, MercadoLibre, PrestaShop, BigCommerce— con el mismo esquema de salida, la parte que se come el tiempo deja de ser el fetch y pasa a ser normalizar cada catálogo sin perder el EAN ni el stock por vendedor.
